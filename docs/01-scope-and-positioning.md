# Ⅰ. 适用范围与前置条件（必读）

本章是发布前必须先读、且必须写进《项目描述文档》与对外发布说明的内容。工具的价值与成本强依赖于项目形态，选错场景的净收益为负。

## Ⅰ.1 适用对象

- 以 TypeScript / TSX 前端项目为主目标（含 Vue 3 SFC）；Node、Electron 主进程等可被 TypeScript Compiler 解析的项目在检索能力上可用，但不在承诺范围内。
- 存在被其他代码、其他团队或其他仓库消费的公共 API，且变更需要可审计。
- 建议规模：10 万行以上、模块数 > 30、跨模块依赖复杂；百万行级收益最大。
- 有 git 仓库（审计链路需要；索引与查询本身不强制）。

判据比行数更重要：**是否存在"改动会波及外部消费方"的公共契约**。一个 3 万行但被 5 个业务仓依赖的组件库，最该用本工具；一个 30 万行的单人实验仓库，用了反而负收益。

## Ⅰ.2 前置条件与不满足的后果

| 条件 | 要求 | 不满足时的后果 |
|---|---|---|
| 类型检查 | 项目能通过 tsc，建议开启 strict | 自动降级为 `syntax-only`；references 与 impact 不得作为确定性依据，输出首行必须声明降级 |
| 类型完整度 | 尽量避免 any 泛滥与隐式类型 | 只建议使用符号与引用检索，不建议依赖影响分析结论 |
| 路径解析 | 别名写入 tsconfig 或 `nexus.config.json` | 别名解析失败，跨包引用被降级为 heuristic |
| 样式路径解析 | 样式别名写入配置的 `style.aliases` | `~`/`@` 前缀的样式路径降为 unresolved，原因与计数写入 coverage |
| 索引范围 | 忽略规则写在 `ignore` / `include`，全量与增量共用 | 未声明的忽略会缩小"可证明完整性"范围；工具只在索引范围内承诺确定性关系 0 漏报 |
| 配置文件 | 默认 `.nexus/nexus.config.json`（Zod 严格校验） | 缺失时 `build` 输出引导语而非文件系统错误；`.ts` 配置未授权时拒绝执行（E18） |
| 多根工作区 | 每个 root（package）可独立 typecheck，根集合能被识别或显式声明（见 5.7） | 未识别的根不进入索引；跨 root 只允许「已声明依赖 + exports 可解析」的边，其余记 unresolved(package-boundary)；根集合歧义时退出并列出候选根（E15） |
| 版本控制 | 有 git 仓库与可用的 diff 基线 | 审计链路（变更证据、api-diff、postflight）不可用；索引与查询仍可用 |
| 运行环境 | Node ≥ 22.16.0（强制，见 2.2 五层口径）。SQLite 只允许使用内置 `node:sqlite`；本地可执行 tsc，无需常驻服务 | 版本不足直接拒绝运行（E14），不提供降级驱动 |
| 资源 | 磁盘与内存充足 | 大项目构建可能失败或降级；资源不足必须显式报告（E20），不得静默串行处理而不告知 |

## Ⅰ.3 框架支持范围

| 项目类型 | 支持程度 | 说明 |
|---|---|---|
| 纯 TS / TSX（React） | 开箱可用 | 组件 Props 由 TS 类型直接解析；Next 等框架约定类能力有限 |
| Vue 3 | 适配（可解析范围 + 显式降级） | SFC 语义、Props、Emits、Slots 与四类模板引用边；复杂类型降级规则见 4.1.3 |
| CSS / SCSS / Less | 仅文件级依赖 | 索引 @import / @use / @forward、Vue `<style src>`、TS import css；不做类名与选择器消费方；见 4.2 |
| HTML | v1.x opt-in（默认关） | `<link rel="stylesheet">` / `<style src>` 文件级引用，开启后标 experimental；不进 v1 gate |
| JS 与 TS 混合 | 可用 | 纯 JS 部分为语法级，关系标为 heuristic |
| Svelte / Angular 等 | v1 未提供 | 官方不做适配：可自行 fork 后增加适配（不承诺插件接口稳定），或关闭框架层索引 |
| 其他框架 | 仅框架无关能力 | 关闭框架层索引后，仍可使用符号、引用、依赖与影响分析 |

## Ⅰ.4 不推荐引入的场景

- 中小型项目：一次 grep 就能覆盖全部消费方。
- 个人项目、自我娱乐项目、实验性原型、快速验证的想法。
- 无公共 API 契约的单人仓库，或代码生命周期短于索引维护周期的项目。
- 无法保证类型检查通过、且短期内不打算修的项目。

共同点：**固定成本（建索引、维护、认知成本）高于它消除的试错成本**。这类项目引入后通常表现为"每个任务都慢了一点、Token 多了一点，但没解决实际问题"。

## Ⅰ.5 成本与收益口径

| 维度 | 说明 |
|---|---|
| 固定成本 | 首次索引构建与每次增量更新的耗时；磁盘占用（几十 MB 至 GB 级）；峰值内存（百万行级目标 1.5 GB，硬上限 1.8 GB，待 21.2 实测校准） |
| Agent 侧增量成本 | 每个任务多出 3 至 6 次工具调用，以及相应输出体积 |
| 收益 | 消除试错性检索；把变更影响、公共 API 差分、复用检测变成可机检事实 |
| 净效果 | 简单任务（局部实现调整）总耗时与 Token 可能净增；跨模块、动公共 API 的任务通常净减 |

对外表述必须用这个口径：**固定成本上升，探索成本下降**。严禁笼统宣称"节省 Token"，它与"引入后每任务可能更耗时"的事实相冲突，会直接损害可信度。

## Ⅰ.6 对外发布说明（底稿）

**适用范围**：适用于可被 TypeScript Compiler 解析的项目（含 TSX）。建议 10 万行以上、多模块，且存在被其他代码或团队消费的公共 API；需要 git 仓库。

**类型前提**：项目需能通过 tsc 检查，建议 strict。类型越松散，确定性结论越弱；any 较多的项目请只使用检索能力，不要依赖影响分析。

**完整性口径（v1.24 修订）**：工具承诺的"零漏报"仅适用于**确定性静态关系**（在声明的语言、语法、配置与依赖范围内，可由 TypeScript / Vue 语义分析判定的关系），且仅适用于**已完成分析的成功覆盖范围**。启发式关系带置信度标注；动态关系（动态 import、运行时拼接路径、反射、运行时注册、动态组件）明确不保证完整识别。工具不会把"未发现"表述为"确认不存在"，除非覆盖完整且分析成功。

**框架支持**：TS / TSX 开箱可用；Vue 3 适配限于可解析类型与四类模板边，复杂 Props / Slot 类型显式降级（见 4.1）；CSS / SCSS / Less 只做文件级依赖（见 4.2），不提供类名与选择器消费方；HTML 的文件级引用为 opt-in（默认关、标 experimental）。Svelte、Angular 等 v1 未提供适配，需自行 fork 适配，或关闭框架层索引。

**不推荐**：中小型项目、个人与娱乐项目、实验性原型、无公共 API 契约的单人仓库。这类项目引入后的固定成本高于收益。

**成本**：首次建索引与增量更新有固定耗时；额外占用磁盘与内存；Agent 任务会多出数次工具调用。简单任务的耗时与 Token 可能净增，跨模块与公共 API 变更任务通常净减。

**安全**：默认只读、默认离线、默认不执行被分析项目的任何代码。配置文件默认是 JSON 数据，不被执行；`.ts` 配置必须在用户显式授权后才作为可执行代码加载，未授权即拒绝（E18）。

**收益**：在十万行以上、契约密集的仓库中，让变更影响、公共 API 差分、复用检测成为可复核的事实；约束文档仍然必需，但不必再靠人工盯守。

## Ⅰ.7 承诺表述纪律（v1.24 新增）

对外文案、错误信息、日志、阶段报告、AGENTS 模板中，**禁止出现以下表述**：

| 禁止表述 | 允许的替代 |
|---|---|
| "完整调用图" | "带置信度标注的静态调用关系" |
| "零漏检 / 100% 准确"（无限定） | "确定性静态关系在已覆盖范围内 0 漏报" |
| "始终实时 / 永远最新" | "fresh 状态下与已确认源文件版本一致；dirty / indexing / stale 会显式标注" |
| "符号 ID 永不变" | "身份迁移有置信度；高置信迁移保持 ID，低置信一律创建新 ID" |
| "节省 Token" | "固定成本上升，探索成本下降" |
| "自动修复索引问题" | "`doctor --repair` 仅修 Nexus 自身数据，不改源码与项目配置" |

以上任一条无论出现在何处，评审均可判为文档缺陷并阻断冻结。---

# 1. 定位与价值主张

## 1.1 问题定义

在超大型前端项目中，AI CLI Agent 可用的手段只有文本搜索、目录浏览和有限的上下文窗口。它读到一个符号的 3 处引用，就会认为只有 3 处，然后动手修改公共签名——这是"静默漏报"（silently wrong），而不是报错。

在注重公共 API 稳定性、一致性与复用性的项目里，静默漏报的代价远高于报错：一个看似无用的导出被删除、一处重复实现被新建、一处隐式依赖被改断，都不会触发任何提示，却在数月后以契约破坏的形式暴露。

因此本工具不是"更好的搜索工具"，而是**以确定性索引为底座的变更审计与 API 治理设施**：人在终端可复核，CI 可拦截，Agent 可通过 MCP 取得可复核的事实。搜索只是它的下沉能力。

## 1.2 三条不可替代的能力

**1. 可验证的完整性（negative evidence）**

能明确回答"该符号共 N 处引用，已全部列出，无其他引用""该 API 无外部消费方，可安全删除""以下 K 处关系无法静态解析，需人工确认"。

完整性必须是可验证的结论，不能写"可能还有其他"。但"可验证"有严格前提，v1.24 将其限定为三条同时成立：

1. 该关系属于**确定性静态关系**（5.3 的 `relationClass = certain`）；
2. 该文件在索引范围内（未被 `ignore` 排除，未被降级跳过）；
3. 该次分析成功完成（不是 `failed`，不是 `stale`，不是 `syntax-only`）。

三条缺一，输出只能写"在当前覆盖范围内未发现"，并同时给出覆盖范围与未覆盖原因。**禁止用"未发现引用"表达"确认不存在引用"。**

**2. 确定性可复现**

同一 commit、同一命令、同一参数、同一构建指纹，输出逐字节一致。这是人与 AI 看到同一份事实、以及把工具放进 CI 做门禁的前提。

**3. 增量下的身份可判定**

文件重命名、移动、barrel 重导出**不必然**改变符号身份。工具必须给出身份是否延续的判定与置信度：高置信时继承 ID，中低置信时保守处理（保留歧义或创建新 ID），不得为了让"身份稳定"好看而强行合并。详见 5.2。

## 1.3 明确的非目标（v1 不做）

- 不做 IDE、不做语言服务器、不替代 tsserver / LSP；语义结论必须能与 LSP 交叉校验。
- 不追求全语言覆盖，v1 只承诺 TypeScript、TSX、Vue SFC、JSON 与常见配置文件；样式文件只做文件级依赖（见 4.2）。
- 不宣称"完整调用图"，只提供带置信度标注的静态调用关系。
- **不做运行时追踪**：不注入探针、不采集运行时调用计数、不做覆盖率插桩。因此"运行时实际调用频率"永远不在能力范围内（P1-06）。
- 不做代码生成、不做自动修复、不修改被分析项目的业务代码。
- 不以"节省 Token"作为价值主张。Token 消耗下降是完整性与精确性的副产品，不作为独立验收指标。
- 不提供样式类名 / 选择器的消费方全集，不把 `.btn` 这类选择器当作可查询符号；样式能力止于文件级依赖与反向依赖。
- 不做 Sass / Less 编译，不解析变量拼接后的路径，不读取项目外文件，不访问网络。
- 不提供自动迁移旧索引的承诺：Schema 不兼容时默认重建（5.5）。

## 1.4 最小成功判据（可执行的验收定义）

在一个真实的中大型 Vue 3 + TypeScript 项目中执行同一条变更：修改一个公共符号的签名。工具须输出：

1. 受影响引用全集（含总数、分类计数与不可解析项清单）。
2. 受影响的公共 API Surface 与语义化差分（breaking / additive / internal）。
3. 关联测试与建议执行的验证命令。
4. 静态分析盲区声明。

**验收口径（v1.24 修订，替代原文"引用漏报率必须为 0"）**：

| 项 | 定义 |
|---|---|
| 统计对象 | 仅 `relationClass = certain` 的引用边 |
| 分母 | 独立 Oracle（tsserver / LSP）在**同一 tsconfig、同一 TS 版本、同一文件集合**下确认存在的引用总数 |
| 分子 | 工具输出的、同位置的确定性引用条数 |
| 通过线 | 漏报率 = 0（合格样本为 16.1 定义的验收夹具集与抽样集） |
| 不计入 | heuristic 边、dynamic-unresolved 边、被 ignore 排除的文件、降级跳过的文件（须逐类单列计数） |
| 失败判定 | 出现"整类漏报"（某一语法形态的引用系统性缺失）即判不成立，不论总体召回率多高 |

若确定性关系的漏报率不为 0，本项目不成立，其余能力不予验收。

## 1.5 设计原则（v1.24 新增，全文档冲突时的裁决依据）

当后续章节出现未覆盖的取舍时，按以下顺序裁决，顺序即优先级：

| 序号 | 原则 |
|---|---|
| 1 | 宁可明确承认无法分析，也不能伪造确定结果 |
| 2 | 宁可保留旧索引，也不能提交不一致的新索引 |
| 3 | 宁可将符号标记为身份不确定，也不能错误合并两个符号 |
| 4 | 宁可降低并行度，也不能突破资源安全边界 |
| 5 | 宁可要求用户授权，也不能隐式执行不可信代码 |
| 6 | 宁可报告性能不达标，也不能通过改变测试口径制造达标结果 |
| 7 | 宁可暂停并提交架构问题，也不能由 AI Agent 擅自改变系统设计 |
| 8 | 宁可将功能标记为 partial，也不能用模拟实现冒充真实能力 |

原则 1–8 是评审依据：任何设计若违反，评审可直接拒绝，无需再讨论实现成本。
