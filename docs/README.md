# Anemia Nexus 项目文档

> **文档名称**：《Anemia Nexus》技术设计与开发任务书
> **版本**：v1.24（架构评审修订版）
> **基线**：v1.23 评审修订版 / v1.0 rev 29
> **适用对象**：项目负责人、架构评审人员、AI Coding Agent
> **文档状态**：**v1.24 已冻结（2026-11-12）**；Phase 00–04 已关闭（Phase 03/04 为 pass，负责人 2026-11-13 评审）；Phase 05 已关闭（pass）；Phase 06（增量、性能与一致性）已关闭（`pass-with-limits`，负责人 2026-11-13 接受并允许进入 Phase 07）；Phase 07（复用性、MCP 与交付）已实现，G0–G12 通过/带限制，等待负责人评审。各阶段入场与实施记录见 `phase-00/` … `phase-07/`。

本目录是 Anemia Nexus 的技术规范主体。内容由上述任务书按章节拆分而来，**技术内容原文照录，未做改写**；每个文件头部标注了来源章节。

> 原始任务书不存放在本仓库。本目录即当前工作区的规范依据；如需变更规范，必须走评审与版本化流程（见文末「文档变更纪律」），不得由实现者就地改写。

## 1. 建议阅读顺序

1. `01-scope-and-positioning.md`：先判断项目定位、适用对象、非目标与最小成功判据。
2. `02-technical-baseline.md`、`03-tech-stack-and-build.md`：技术基线与选型结论。
3. `04-architecture.md`、`05-data-model.md`：分层架构、索引管线、符号身份与存储模型。
4. 按任务涉及的领域阅读第 6–18 章。
5. `19-delivery-phases.md`、`20-prohibitions.md`、`21-phase-00.md`：阶段门禁、禁令与 Phase 00 要求。
6. `appendix-a-d.md`：兼容矩阵、文档职责、冻结清单与修订对照。

## 4. 文档职责边界（依据附录 B）

| 文档 | 唯一职责 | 不该写什么 |
|---|---|---|
| 本目录（技术设计） | 架构、数据模型、模块职责、接口与验收约束 | 逐步操作教程、具体安装命令的长篇解释 |
| 根目录 `README.md` | 安装、运行、配置、上手顺序、能力边界 | 内部数据模型细节、实现取舍的历史争论 |
| `.dsh/AGENTS.md` | 项目级 AI 协作规则、开发约束、关键入口 | 工具用法全集、错误码表 |
| `docs/runtime-api.md` | Node API 最低版本清单 | 架构决策 |
| 阶段报告（后续建立） | 实施结果、测试证据、遗留问题 | 设计变更理由（应回写到规范） |

冗余控制规则：

1. 同一份规则只允许一个权威来源；需要重复表达时写成引用（「见 12.4」），不复制内容。
2. 错误码表、状态名、字段名三类内容不得在多个文档中各存一份，一律引用本目录。
3. 修改权威来源时，必须在同一次提交中检查所有引用点。
4. 两处内容不一致时，以本技术规范为准并修正另一处，不得"两个都留着"。
5. 文档版本与代码版本必须可对应：阶段报告注明所依据的规范版本（v1.24）。

## 5. 文档变更纪律

- 本目录的技术内容与任务书 v1.24 一致。任何对架构、数据模型、接口、验收口径的修改，都属于规范变更，必须由项目负责人确认并形成新的版本记录。
- 实现过程中发现文档冲突、缺失或无法落实时，先记录问题与影响，按 `20-prohibitions.md` 的 20.6 提交《架构问题报告》，**不得自行修改规范或作出架构级决策**。
- 新增跨章节概念时，必须同步更新 `23-conflicts.md` 或登记到对应章节，否则视为文档缺陷（第 23 章维护规则）。
