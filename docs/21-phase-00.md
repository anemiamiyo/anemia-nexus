# 21. Phase 00 具体执行要求

Agent 收到任务后，首先执行 Phase 00。Phase 00 不以编写完整系统代码为目标，而是完成可行性验证与结论输出。**Phase 00 的结论具有否决权**：任一 P0 项无法验证通过，就停下并提交架构调整申请，不得"先做着看"。

## 21.0 Phase 00 的十组验证（v1.24 新增）

| 组 | 验证内容 | 判定方式 | 交付物 |
|---|---|---|---|
| G1 | SCIP ↔ TS Compiler API 符号映射 | 4.3.4 的 T01–T08 自动化用例 | 映射对照报告（成功率、误匹配、漏匹配、冲突样例） |
| G2 | Vue SFC 语义与模板引用映射 | T09 + vue-tsc 抽样对照 | 用户符号集合一致性报告、四类模板边样例 |
| G3 | 声明合并、重导出、别名、跨包引用 | T02–T05、T08 | 逐场景结论（成立 / 不成立 / 需限制） |
| G4 | 文件移动/重命名后的身份策略 | 5.2.8 八场景原型验证 | 八场景迁移结果 + 置信度 + 判定依据样例 |
| G5 | SQLite WAL 与 manifest 的一致性方案 | 12.3.3 七注入点原型（可用脚本模拟） | 恢复矩阵（现场 → 动作 → 结果） |
| G6 | Node 运行环境与所需 API | 在 22.16.0 与当前 LTS 上跑安装/构建/CLI/DB/索引/MCP | API 最低版本清单 + 双版本结果 |
| G7 | 不同规模的真实 RSS | 5 万 / 30 万 / 100 万（生成器）三档 | 按 16.2.3 字段的完整测量记录 |
| G8 | 多根项目资源调度可行性 | 3 root 并行 + 压预算（F18 原型） | 降级阶梯实测 + 是否破坏旧索引的结论 |
| G9 | 配置安全边界 | F17 七用例 | 安全验证报告（含断网执行记录） |
| G10 | 全量与增量结果一致性 | 12.2 十项比较（在最小仓库上） | 等价性报告 + 首批差异样例 |

补充要求：

- 每组的**判定门槛必须在验证开始前写定**（例如 G1 的 `mappingSuccessRate` 门槛、G7 的内存上限），验证后不得调整。门槛变更记录必须与原门槛同时存档。
- 所有验证必须在**独立的最小测试仓库**上完成，不得在真实业务项目上"顺手验证"。
- 每组结论必须三选一：`pass` / `pass-with-limit`（附限制条件）/ `fail`（附架构调整建议）。不存在"基本通过"。

## 21.1 项目描述文档（Phase 00 必交付）

Phase 00 必须产出一份《项目描述文档》（`README.md` 或 `PROJECT.md`），作为仓库入口文档与对外发布说明的底稿。该文档决定"用户读完 5 分钟内能否判断自己该不该用"，属于阶段 00 的验收项。

必含内容：

1. 一句话定位与非目标（本工具做证据，不做判断）。
2. 适用范围：可被 TypeScript Compiler 解析的项目（含 TSX）；建议 10 万行以上、模块数 > 30、存在被其他代码或团队消费的公共 API；有 git 仓库；多 package 仓库按 root 分别建索引，不得合并（5.7）。
3. 前置条件与不满足时的后果：Node ≥ 22.16.0（低于该版本 E14 退出）；能通过 tsc（建议 strict）；路径别名须写在 tsconfig 或配置；monorepo 每个 package 需可独立 typecheck；审计链路依赖 git。
4. 框架支持矩阵：TS/TSX 开箱可用；Vue 3 限于可解析类型与四类模板边，复杂类型显式降级；Svelte、Angular 等 v1 不提供适配。
5. 不推荐引入的场景与判据。
6. 成本与收益口径（Ⅰ.5）。
7. **完整性口径**（v1.24 新增，照抄 Ⅰ.6）：三类关系、零漏报的适用范围、`partial` 的含义。
8. 最小成功判据（1.4 的可执行版本，含分子分母）。
9. 安装与上手顺序：安装 → 手动接入（MCP / AGENTS.md / Skill）→ init → build → status，各附一条可直接复制的命令。
10. 索引目录（`.nexus/`）、基线文件（`nexus.baseline.json`）与版本管理约定。
11. 安全与隐私边界：默认只读、默认离线、不执行项目代码；**配置默认是 JSON 数据，`.ts` 配置需显式授权**（18.3）。
12. 已知限制：动态关系与 opaque 边界不可判定；未提供的能力必须明确标注"未提供"。
13. Vue 工具链基线：记录 `@vue/language-core`、`vue-tsc`、TypeScript 三者版本组合（4.1.6）。
14. **运行环境矩阵**（v1.24 新增）：开发 / 最低支持 / CI / 构建 target / API 依赖五层（2.2）。
15. **索引健康与状态说明**（v1.24 新增）：五态含义、`partial` 与 `degraded` 的读法、如何判断结论强度。

写作约束：不得宣称"节省 Token"作为核心卖点；不得宣称提供完整调用图；不得把规划中的能力写成已实现；不得声称工具会自动写入 AGENTS.md、MCP 配置或 Skill 目录；不得承诺字号可调。文档须在 Phase 00 结束时随技术选型报告一并提交，并在后续阶段随能力变化同步更新。

另须写明「安装之后的手动接入」四步，并说明工具不代写任何配置：

1. MCP：运行 `nex print mcp-config --client dsh`，把打印出的 JSON 合并进平台的 MCP 配置，重启平台。
2. AGENTS.md：运行 `nex print agents`，把片段粘贴到项目根目录的 AGENTS.md；若已存在则追加，不得覆盖原内容。
3. Skill：从仓库下载 `skills/nexus` 目录，复制到平台的 skills 目录（以 dsh 为例为 `~/.dsh/skills/nexus`，实际路径以平台文档为准）。
4. 验证：`nex status` 应返回 `state` 为 `uninitialized` 或 `ready`，且 `self.serverVersion` 与所安装的包一致；已完成 build 的项目应为 `ready` 且 `staleness` 为 `fresh`。

必须在文档中明写：工具不提供任何 `--write-*` / `--install` 参数，MCP 配置、AGENTS.md 片段与 Skill 一律只打印到终端。

## 21.2 构建内存预算与实测校准（v1.24 修订，P0-05）

### 21.2.1 待校准目标值

内存不采用"够用就行"的口径，但也不再把下列数字当作**已证明**能力。它们是 Phase 00 的**校准目标**，实测后固化；不达标时按 21.2.4 降级能力，不放宽预算。

| 规模（约） | 构建峰值内存（目标） | 硬上限 | 查询常驻内存 | 索引体积 |
|---|---|---|---|---|
| 5 万 LOC | ≤ 400 MB | 550 MB | ≤ 60 MB | 5–15 MB |
| 30 万 LOC | ≤ 700 MB | 900 MB | ≤ 100 MB | 40–60 MB |
| 100 万 LOC | ≤ 1.5 GB | 1.8 GB | ≤ 200 MB | 150–250 MB |

### 21.2.2 测量口径（必须写进报告，缺一项即无效）

| 项 | 口径 |
|---|---|
| 峰值 RSS | 构建子进程的 `process.memoryUsage().rss`，每 50ms 采样，取最大值；不含 CLI 父进程的交互开销（父进程单独记录） |
| 构建范围 | 明确是单 root 还是多 root 并行；多 root 时必须分别给"单 root 峰值"与"全局峰值" |
| 是否含 SCIP | 若为对比目的关闭某阶段，必须标注"不含 X"，不得混入主结论 |
| Vue 投影 | 按 4.1.1 的临时物化方式统计（同一时刻只保留受影响的影子文件） |
| SQLite | 写批次大小、是否 WAL、DB 文件大小需同时记录 |
| 重复次数 | ≥ 3 次，取中位数与最大值，两次之间需重启进程（避免堆复用） |
| 环境 | 按 16.2.3 全字段记录，尤其 Node 版本与可用内存 |

### 21.2.3 实现约束（属于验收项，不是优化建议）

1. **只做一次类型检查**：SCIP 索引与自有分析器必须复用同一个 Program，或直接以 SCIP 符号结果配合轻量语法遍历；禁止两套类型检查并行。
2. **边算边写**：构建过程必须流式写入 SQLite 并分批提交，禁止把全量结果攒成内存对象后再序列化；任何"先 stringify 巨型数组"的实现视为不通过。
3. **紧凑结构**：字符串 interning + 整数 ID；引用与调用边使用定长数组而非对象；ts-morph 必须分批加载并显式释放 AST。
4. **可观测**：build 与 update 必须输出峰值 RSS、各阶段耗时、写入行数；CI 对峰值内存设阈值，超限即判失败。
5. **Vue 投影的计入方式**：SFC 投影与内存映射的峰值已计入上表；统计口径按 4.1.1（不持久化全量 shadow），不得用"常驻全量 shadow"实现后再声称超预算。

### 21.2.4 不达标时的处理（按顺序，不得跳级）

1. 关闭 calls 索引（保留 references 与 dependencies）→ 重测。
2. 分块构建（按目录分批，释放 AST）→ 重测。
3. 降低 Vue 投影粒度 → 重测。
4. 单 root 串行（并发位降为 1）→ 重测。
5. 若仍不达标：报告实测数据，提交架构调整申请（20.6），由负责人决定缩小承诺范围（例如百万行档明确不支持）。

**禁止**：以"机器内存够用"为由放宽预算；只测一次就宣布达标；把峰值 RSS 改成"平均 RSS"或"RSS 减去共享库"来制造达标。
