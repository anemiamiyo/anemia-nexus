# 22. 首次接入与失败体验（零前置自举）

MCP、AGENTS.md 与 Skill 三件套都属于软约束：它们决定 Agent "会不会用"，但没有任何一环能强制"索引已经建好"。本章把这条链路写成硬性要求。

## 22.1 典型失败路径

| 现象 | 成因 | 后果 |
|---|---|---|
| Agent 首次调 status 拿到错误码后改用 grep | 状态工具以错误形式返回，Agent 自行降级且不告知 | 静默不生效：用户以为在用工具，结论却来自裸检索 |
| Agent 自行执行 build 失败 | 未安装，或命中 npm 上同名的旧 nex 包 | 返回无关帮助文本，用户判定工具不可用 |
| 跳过 init 直接 build | 缺少配置文件，错误只报缺失不报下一步 | 卡在引导环节 |
| 项目类型检查存在既有错误 | 自动降级 syntax-only 但未在结果中声明 | 把不完整事实当确定性结论，改错公共 API |
| 浅克隆或没有可用基线 | postflight 依赖 git diff 基线 | 审计失败，被误判为工具损坏 |
| **（新增）** `.ts` 配置未授权 | 用户从旧文档照抄了 `.ts` 配置 | E18 报错但没说怎么授权，用户以为工具坏了 |

## 22.2 硬性实现要求

1. **status 永不报错，作为引导态。** 索引不存在时返回 `state: uninitialized`，并附四组信息：
   - 环境检查（Node 版本、tsconfig 是否存在、类型检查结果、git 是否可用、配置格式与是否需授权）；
   - 下一步命令（可直接复制的完整命令串）；
   - 预估耗时（按规模给区间，口径见 22.3）；
   - 接入物料获取命令（`nex print mcp-config` / `nex print agents` / `nex print skill`）。

   其他工具此时才返回 E01。若检测到多个 root，引导态必须列出候选根（名称、路径、是否已建索引）并询问"分别建索引 / 只选部分"，不得默认全选或默认跳过。引导态默认按 TTY 渲染：TTY 输出 pretty，非 TTY 输出 lines；两种形态的**信息量必须相同**。

2. **零前置自举。** 提供 `nex mcp --auto-bootstrap`：启动时若无索引，在后台异步构建；`status` 返回 `state: indexing` 与进度百分比，其余工具返回「未就绪、预计还需 X 秒、可用 status 查询进度」，不返回错误码。默认关闭，安装文档建议与 `--watch` 一起开启。

3. **缺配置不裸报错。** `build` 发现缺少配置时，输出「未找到配置文件，执行 `nex init --yes` 后重试」；若发现未授权的 `.ts` 配置，输出「检测到 TypeScript 配置，它会被作为代码执行。授权：`nex build --trust-config`；或改为 JSON：见链接」并给出 E18。

4. **二进制自证。** `status.self` 必须返回 `serverVersion`、`packageName`、`binaryPath`、`projectRoot`、`nodeVersion`。若用户调用的是 npm 上同名的旧 nex 包，包名与版本不符可一眼识别。

5. **降级可见。** 每次响应首行标记当前模式（`normal` / `syntax-only` / `scoped`）与 `degraded`；postflight 输出 `confidence` 字段；低置信度时禁止自动触发 `--fail-on` 阻断。

6. **错误只进 stdout。** 错误、诊断、报告一律不写入项目文件或新建目录（16.4）。

7. **（新增）状态必须区分"首次可用"与"全部完成"。** `state` 只有 `uninitialized` / `ready` 两值，但 `staleness` 与 `roots[]` 必须能表达"部分 root 已可用"。禁止把"正在构建"说成 `ready`。

## 22.3 可验收的体验指标（v1.24 修订，跨章节冲突 23.3）

v1.23 的"3 个动作、2 分钟拿到第一份索引结果"与"30 万行全量 ≤ 120s"是两个不同量级的事，混在一起会给出错误预期。v1.24 拆成四个时间点，分别验收：

| 时间点 | 定义 | 目标（30 万行项目） | 验收方式 |
|---|---|---|---|
| `T0→T1` | 安装 → 看到引导态（`status` 返回 `uninitialized` 且四组信息完整） | ≤ 30s | 自动化：干净目录安装 tarball，跑 `nex status` |
| `T1→T2` | 引导态 → 发出第一条构建命令（动作数 ≤ 3） | ≤ 2 分钟 | 人工 + 录屏；动作定义为"复制粘贴一条命令"或"确认一次" |
| `T2→T3` | 构建开始 → **首个 root 可查询**（`staleness = fresh`） | ≤ 120s | 自动化：轮询 `status`，记录首次 `fresh` 时刻 |
| `T2→T4` | 构建开始 → **全部 root 完成** | ≤ 180s（多 root 并行按 5.10 调度） | 自动化：等到 `roots[]` 全部 `fresh` |

规则：

1. **两分钟目标只覆盖 `T1→T2`**，不承诺"两分钟内完成全量索引"。
2. 超过 120s 仍无任何 root 可用时，`status` 必须给出进度与预计剩余时间，不得静默。
3. 百万行档不设 `T2→T3` 硬指标（不进 CI），但必须给出实测值并写入文档。
4. 全过程不得出现「没有任何下一步」的失败态。首个可预见的失败态必须是 Node 版本不足（E14）。
5. 从 MCP 调用拿到的首个结果必为 lines 紧凑格式，不随客户端环境变化；需要人类视图只能走 CLI 的 `--format pretty`。
